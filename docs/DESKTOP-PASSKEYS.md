# Desktop wallet passkeys on macOS

Desktop uses AuthenticationServices platform passkeys on macOS 15 or later. The app requests user verification and derives 24 English BIP39 words from the 32-byte WebAuthn PRF result for the UTF-8 label `Default`. The RP is `keys.kaleidoswap.com`. Registration returns the public credential ID. A separately confirmed assertion with that ID must succeed before the wallet is created. The native commit checks its public fingerprint against the latest successful assertion in memory and consumes that proof after the wallet is saved. An assertion without an ID lets the user choose an existing discoverable Desktop credential after reinstalling. Restoring the phrase works independently of the passkey provider.

The current Chrome extension uses its extension ID as its RP. To move a wallet between the current extension and Desktop, use its recovery phrase.

Earlier extension test builds used `keys.kaleidoswap.com`. Register a new **KaleidoSwap Desktop** credential during Desktop setup. The provider may also show credentials left by those tests. Desktop checks the versioned user handle on every assertion and reports `passkey_legacy_test` for an unrecognized credential before using its PRF output. Select a Desktop credential or enter the old wallet's recovery phrase. The marker distinguishes new Desktop credentials inside the shared RP. The domain is the security boundary for clients authorized to use it. The system passkey provider controls credential syncing.

## Provision a macOS distribution

The Desktop beta workflow reads the base64-encoded Developer ID provisioning profile from the Actions secret `APPLE_BETA_PASSKEY_PROFILE` on `dev` and beta tags. It prepares the signing inputs, enables the overlay, then verifies the embedded profile and signed entitlements in the final app. If the secret is absent, the build offers phrase-based wallets.

1. Authorize Associated Domains for the exact Apple App ID of the binary being signed (for example, `com.kaleidoswap.beta` for the beta). Create a matching Developer ID provisioning profile using that team's signing certificate.
2. Serve a public HTTPS JSON document at `https://keys.kaleidoswap.com/.well-known/apple-app-site-association`. Its `webcredentials.apps` list must include the complete application identifier from each authorized profile. Apple's association service must be able to retrieve the document without a redirect. Only include Desktop builds intended to share the credential namespace.
3. Generate the signing inputs locally with `python3 scripts/prepare-desktop-passkey-signing.py /path/to/Desktop.provisionprofile com.kaleidoswap.beta`. This reads the selected profile, checks the bundle ID, entitlement and expiry, then writes the profile and signing entitlements under the ignored `src-tauri/target/passkey-signing` directory.
4. Build with Xcode 16 or later and the beta release's usual Developer ID signing and notarization settings. Append `--config src-tauri/tauri.passkeys.conf.json` to the normal macOS Tauri build command **after** the requested beta/P2P overlays. The overlay embeds the profile, selects these entitlements and enables the Swift bridge.
5. Verify the signed app with `codesign --verify --deep --strict`, `codesign --display --entitlements -`, `xcrun stapler validate` and `spctl --assess --type execute`. On a provisioned Mac, test creation, a fresh prompt using the returned ID, discovery in a clean test profile, and export. Confirm the same recovery phrase or public fingerprint for each assertion.

The app checks the signed Associated Domains and application-identifier entitlements, Apple signing chain and embedded profile before offering the feature. AuthenticationServices checks the actual domain association and provider during the system prompt. A stock beta, unsigned development app or unsupported OS offers the phrase-based path. A provider without WebAuthn PRF cannot derive a wallet. Windows exposes Win32 WebAuthn without verifying the caller's RP association. Windows and Linux currently offer recovery phrases.
